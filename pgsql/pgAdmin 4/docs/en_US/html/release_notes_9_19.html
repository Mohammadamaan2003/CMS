Version 9.19¶

Release date: 2026-10-29

This release contains a number of bug fixes and new features since the release of pgAdmin 4 v9.18.

Warning

In server mode, free-text Password Exec Commands are no longer run, and ENABLE_SERVER_PASS_EXEC_CMD is deprecated and ignored. Administrators now define the permitted commands by name in SERVER_PASSEXEC_COMMANDS, and users choose one of those names in the server properties. Configure SERVER_PASSEXEC_COMMANDS before the first start after upgrading: on that start, each existing command that exactly matches a configured entry is converted to its name, and every other command is cleared, which cannot be undone. If the setting is empty, the conversion is postponed and a warning is logged at each start. See config.py and the server dialog documentation for details.

Note

Users who do not own a shared server never inherit the owner’s password file; it is treated like the owner’s password, SSH key and SSL client files. Each user can set their own password file on their copy of the server, and a file that everyone should use can be placed in a SHARED_STORAGE directory and referenced as Name:/.pgpass.

Note

In desktop mode, when an SSH tunnel is configured with an identity file or a password, pgAdmin no longer also offers keys from the SSH agent; the agent is still used when neither is configured. In server mode, SSH tunnels never use the SSH agent, or the keys and configuration in the ~/.ssh directory of the account pgAdmin runs as, so a tunnel that relied on them must be given an identity file or password on the server.

Note

On Python 3.10 and later, pgAdmin now requires Flask-Security-Too 5.8.3 or later, which fixes an open redirect (GHSA-ccgp-pv8r-95wm). This matters to anyone installing pgAdmin from the Python wheel into an existing environment. Python 3.9 installations remain on the Flask-Security-Too 5.6 series.

Supported Database Servers¶

PostgreSQL: 14, 15, 16, 17 and 18

EDB Advanced Server: 14, 15, 16, 17 and 18

Bundled PostgreSQL Utilities¶

psql, pg_dump, pg_dumpall, pg_restore: 18.6

Issue #10645 - Fix connection redirection in the materialized view refresh, where the target database’s name was passed straight to psql’s --dbname: because libpq expands a value containing an equals sign into a full connection string, a database named like host=... port=..., which any role with only CREATEDB can create, redirected psql to a server of the creator’s choosing and leaked the connecting user’s saved password (CVE-2026-116252). The name is now passed through the same connection-information helper as the Backup, Restore, Maintenance and Import/Export tools, so libpq treats it strictly as a database name. Reported by Bae Seung-won (@baeseungwon1010).
Issue #10646 - Fix a user’s other sessions surviving a password change, which left a session an attacker already held valid after the password was changed or reset (CVE-2026-116251). A self-service change now rotates the user’s fs_uniquifier, logging out every other session while the changing session stays signed in with its database connections, and saved passwords, including those of shared servers, are re-encrypted under the new key, with any that cannot be decrypted cleared, and all of them cleared if re-encryption fails. An administrator reset (including setup.py update-user) also rotates fs_uniquifier, ending all of that user’s sessions, but does not re-encrypt their saved passwords. Reported by Zohaib.
Issue #10647 - Fix time-of-check to time-of-use symlink races in Import/Export Servers and the File Manager’s upload, save and file-open paths, where a path validated against the user’s storage directory was then opened by name, so a symbolic link swapped in at the file or any parent directory in between let an export overwrite, or an import read, a file outside the storage directory (CVE-2026-116250). In server mode on POSIX the file is now opened by walking down from the storage directory one component at a time with O_NOFOLLOW; new files are created with mode 0600 and only regular files are read, opened non-blocking so a FIFO cannot hang the request. Symbolic links inside a storage directory are now refused, even when they point elsewhere inside it. Windows and desktop mode are unchanged, so the race remains there. Reported by MUTED CYBERSECURITY S.L.
Issue #10648 - Fix the same symlink races in the files handed to Backup, Restore and Import/Export Data, where the validated path was passed to pg_dump, pg_dumpall, pg_restore or psql, which opened it by name later, extending the fix for the vulnerability tracked in Issue #10647. In server mode on POSIX pgAdmin now opens the file itself with the descriptor-relative O_NOFOLLOW walk, accepts only a regular file and hands the utility /dev/fd/N, and new backup and export files are created with mode 0600. This applies on Linux only, and not to directory-format Backup and Restore, where the utility opens the files inside the directory by name; on macOS and the BSDs the file is checked safely but the utility still reopens it by name.
Issue #10649 - Refuse hard links and FIFOs in the symlink-race fixes of Issue #10647 and Issue #10648, since O_NOFOLLOW stops only symbolic links: in server mode on POSIX, a file with more than one link is refused, for reading as well as before it is truncated for writing, and a FIFO can no longer hang an upload, save or export; Windows is not covered. The Import/Export Servers, save, Backup, Restore and Import/Export Data handlers also return the reason for a failure instead of text containing the absolute storage path.
Issue #10650 - Fix connection file paths escaping the user’s storage directory, where a password file, SSL certificate, key or CRL, or SSH tunnel identity file such as ../<another user>/.pgpass was joined to the storage directory after stripping only leading slashes, so a user could connect with another user’s credentials or key, and where sslkeylogfile was copied into the connection string unchanged, letting libpq create or append a file as the pgAdmin service account (CVE-2026-116249). In server mode the resolved path, with symbolic links followed, must now stay inside the user’s storage directory or the named shared storage directory, and sslkeylogfile is confined the same way. Connection parameter keys are also validated against the libpq keyword list, since a crafted key could smuggle its own keyword=value pairs past these checks. Servers whose file paths reach outside the storage directory, through .. or a symbolic link, stop connecting until the files are moved into it or into a SHARED_STORAGE directory.
Issue #10651 - Fix any user able to register a server being able to share it with every other user in server mode, because the create and update endpoints stored whatever shared value they were sent, and the servers.json import removed a non-administrator’s shared entries only after validation, so an early error left them in place (CVE-2026-116248). Such requests are now refused with a 403, and the import prunes and skips a non-administrator’s shared entries before validating. The restriction is not retroactive: servers shared by non-administrators before the upgrade stay shared until the owner un-shares them or an administrator clears the shared column in the configuration database, and pgAdmin only logs a warning about each of them at startup, so administrators should review those servers and un-share any that should not be shared. Shared in a servers.json import must now be the JSON value true, and a file that fails validation is refused as a whole.
Issue #10652 - Stop libpq using the pgAdmin service account’s own client files in server mode: when a server had no password file, client certificate or client key configured, libpq fell back to the service account’s ~/.pgpass, ~/.postgresql/postgresql.crt and ~/.postgresql/postgresql.key (or PGPASSFILE, PGSSLCERT and PGSSLKEY), letting any user connect with the service account’s saved passwords or client certificate (CVE-2026-116247). In server mode each of these parameters is now always given a value, the user’s own file or a path that can never be opened, in the connection string and for the utilities. Server mode deployments relying on the service account’s files, or on passfile, sslcert or sslkey in a connection service entry, must configure them on each server instead, and a server with a client certificate must also have a client key.
Issue #10653 - Fix server passwords being left in pgAdmin’s own process environment, where the password handed to psql and to the utilities was written into os.environ and never removed, so another user’s later psql session or utility inherited it and libpq used it for any connection made without a password of its own (CVE-2026-116246). The password now goes only into the environment of the process that needs it.
Issue #10654 - Restrict connection services in server mode, where any user could set a server’s service, or a service connection parameter, to an entry in the service account’s connection service file and connect with that entry’s credentials, and where a PGPASSWORD or PGSERVICE variable set for that account was used for every connection (CVE-2026-116245). A service may now only be used if the administrator lists it in the new SERVER_MODE_ALLOWED_SERVICES setting, which is empty by default; the servicefile parameter is refused, and PGPASSWORD and PGSERVICE are removed from pgAdmin’s environment at startup. setup.py load-servers also refuses an unlisted service. In server mode, servers that use a service stop connecting until the administrator lists it in SERVER_MODE_ALLOWED_SERVICES in config_local.py, ideally before upgrading. Listing a service shares its credentials with every pgAdmin user, so list only services intended for everyone.
Issue #10655 - Stop libpq using the pgAdmin service account’s Kerberos credentials in server mode, where removing KRB5CCNAME let the Kerberos library fall back to the service account’s default credential cache or client keytab (or its logon, through SSPI on Windows), so any user could answer a server’s GSSAPI request as the service account’s principal (CVE-2026-116244). In server mode KRB5CCNAME and KRB5_CLIENT_KTNAME now point at a file that cannot exist, except that a user who logged in with Kerberos gets their own delegated KRB5CCNAME when connecting to a server with Kerberos authentication enabled. Every other connection also gets gssencmode=disable and, with libpq 16 or later, require_auth=!gss,!sspi; without require_auth, SSPI and gssproxy are not stopped, so upgrade the libpq used by pgAdmin and its utilities to 16 or later. A server whose require_auth allows only GSSAPI or SSPI is refused unless the user logged in with Kerberos. A service listed in SERVER_MODE_ALLOWED_SERVICES takes precedence for psql and the utilities, so it must not set require_auth, gssencmode or gsslib.
Issue #10656 - Fix the utility binary-path guard accepting a path under SHARED_STORAGE, which ordinary users can write to, so a user could point a server type’s binary path at a file placed there and have pgAdmin execute it (CVE-2026-116243). Every SHARED_STORAGE entry is now rejected alongside STORAGE_DIR, after expanding $DIR and .. and resolving symbolic links, so an existing binary path under a shared storage directory stops working. An empty STORAGE_DIR is not covered. Reported by Harsh Singh.
Issue #10662 - Stop SSH tunnels using the pgAdmin service account’s own SSH identity, where sshtunnel always loaded the unencrypted private keys in the service account’s ~/.ssh, read its ~/.ssh/config and could use its ssh-agent, so any user could configure a tunnel that authenticated with the service account’s key (CVE-2026-116242). In server mode the tunnel no longer reads those keys or that configuration, or uses the agent, and an identity file that cannot be found in the user’s storage is reported. Tunnels relying on the service account’s key, config or agent must have an identity file in the user’s storage or a password configured on the server.
Issue #10663 - Fix OS command injection in the Import/Export Data tool, where a query-based export could pass a crafted query past the \copy (...) parenthesis-balance guard through a backslash inside a double-quoted identifier, which psql treats as an escape when standard_conforming_strings is off, exposing a live TO PROGRAM clause that runs an arbitrary command on the pgAdmin host, an incomplete fix for CVE-2026-17566 (CVE-2026-116241). A backslash inside a double-quoted identifier is now rejected, and so is a backslash or null byte in the schema, table or column names of an export or import, which reached the same \copy command through qtIdent(). Reported by Yonghwa Lee (Xint by Theori).
Issue #10674 - Fix the File Manager and the storage-path tools acting on a different path from the one that was checked (CVE-2026-116240): opening, saving and listing files, download, delete, rename, create-folder and upload could name files outside the user’s storage directory, or in another user’s directory whose name begins with the same characters. Every File Manager and storage-path caller now acts on the absolute path that was checked, and in server mode on POSIX files are opened relative to the storage directory without following symbolic links, so symbolic links to directories and hard-linked files inside it can no longer be opened, downloaded or renamed through. The storage directory itself can no longer be deleted.
Issue #10675 - Fix LDAP and Kerberos authentication logging a user in to a different account that shared their username: Kerberos and LDAP looked the account up by username alone, or accepted the account Flask-Security’s internal validation had matched by the email typed, so a Kerberos or LDAP user could be logged in as an Internal account, including the initial administrator, or as another user (CVE-2026-116239). Accounts are now looked up by the authenticated username and the source that authenticated them, and only internal authentication logs in an account from its own form. Webserver users whose username matches an Internal account, and LDAP users with capitals in their username, now log in correctly, and setup.py can update a user without a role and add one without --role. Users who relied on being logged in to an Internal account of the same name now need an account of their own source. Reported by Yves Soete of Blacksight LLC (@yssoe).
Issue #10676 - Fix bypasses of the failed-login limit and of pgAdmin’s own login, password change and password reset checks, where a username in another case or a wrong internal password with LDAP or Webserver authentication also configured was never counted, and where Flask-Security’s own /login, /verify, /change, /reset and /reset/<token> views accepted submissions that skipped the failed-login count and lock, the change password permission, the re-encryption of saved passwords, and the internal-account check on resets (CVE-2026-116238). Every failed internal login is now counted (when MAX_LOGIN_ATTEMPTS is set) and only internal authentication is locked, so a locked Internal account no longer blocks other sources. A login form that posts a password is no longer passed to Kerberos, OAuth2 or Webserver authentication, submissions to Flask-Security’s views are refused with 405, and password resets act only on the internal account.
